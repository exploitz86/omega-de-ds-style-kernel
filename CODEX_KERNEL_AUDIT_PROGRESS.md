### F-022 NOR status and caller propagation re-review (2026-10-16 01:07 UTC)

- **Objective:** resume the documented offline NOR audit after F-009; map current completion polling, documented terminal-error checks, and whether failures can reach catalog/UI callers without guessing hardware revision support.
- **Source examined:** `source/NORflash_OP.c` (`Block_Erase`, `Chip_Erase`, `FormatNor`, `WriteFlash`, `WriteFlash_with32word`, `Loadfile2NOR`); `source/Ezcard_OP.c` (`Read_S71NOR_ID`, `Read_S98NOR_ID`, `Save_info` and wrappers); call sites in `source/ezkernelnew.c`.
- **Operation/caller matrix (verified from source):**
  - Sector erase (`Block_Erase`): bounded address mapping, unlock/erase command, then an unbounded loop requiring two full-word reads equal and DQ7 set. It does not check DQ5 or return a result. Used by `Loadfile2NOR` for each block and its optional patch block; also called by the NOR delete path, whose caller cannot observe failure.
  - Chip erase (`Chip_Erase`): unbounded loop reads NOR base twice and exits on equality; it does not require erased DQ7 data or check DQ5. It also displays progress with three `VBlankIntrWait()` calls per iteration. `FormatNor` clears the in-memory catalog after the `void` call returns, regardless of the flash result. The earlier IME/SWI liveness concern remains unverified, not a finding.
  - Word program (`WriteFlash`): polls equal reads after each word, without data verification, DQ5 handling, timeout, or a result. No in-tree call site was found by `rg`; preserve it as an exposed helper but do not count it as an active path without a caller.
  - 32-byte write-buffer program (`WriteFlash_with32word`): after each 16-word buffer-load command and fixed delays, loops without a bound until two reads of the last word are equal. It does not check DQ5 or DQ1 buffer-abort status or confirm the last programmed DQ7/data value. `Loadfile2NOR` uses it for ROM and optional patch blocks.
  - S71 metadata erase/program (`Save_info`): unbounded equal-read loops for erase and each word/buffer program; ID `0x2202` selects the word path and every other ID the buffer path. The `Save_sav_info`, `Save_NOR_info`, and `Save_SET_info` wrappers all return `void`; settings, save-state index, and NOR catalog callers therefore cannot detect a failure. `Loadfile2NOR` commits its catalog entry after the `void` erase/program calls and returns success; `FormatNor` drops the RAM catalog after its `void` chip erase.
  - Preceding “erase all BBP” sequence in `Loadfile2NOR`: source issues `F0`, unlock, `C0`, `0x80`, `0x30`, then performs exactly `0x15000` reads at `FlashBase_S98 + 0x5C0000`; this is a fixed delay, not status/completion/error detection. ### F-009 manually transferred save behavior checked against launcher source (2026-10-16 01:05 UTC)

- **Objective:** answer whether a save file created on another system can be copied into the save folder after the LFN changes, and identify filename/format conditions from the actual loader.

- **Verified behavior:** the folder is `/SYSTEM/SAVER`. GBA launch derives `<full ROM filename stem>.sav` (the emulator path uses `.esv`). `Process_savefile` opens an existing file by that exact name and uses its file length; `Loadsavefile` reads the file bytes as-is into the save memory, requiring a complete read and capping reads at 128 KiB. The kernel does not detect or convert emulator-specific headers, byte-order transforms, or other wrappers. Thus “copy without issue” is conditional on matching the raw save representation and size; cross-emulator save-format compatibility has not been tested. - **Verified:** erase algorithms perform an internal all-zero preprogram/verify step automatically, without host-supplied control/timing. The S29WS-P, S29PL-J, and S29GL-N sector-erase timing tables explicitly exclude that preprogram step. The manuals reviewed did not provide a separate upper bound for the embedded preprogram step, so these table entries alone do not establish a complete wall-clock upper bound.

The current firmware's stable full-word comparisons are not a documented substitute for the full per-device status procedure. The main `0x223D` ID matches WS512P; the actual supported S71 part remains unknown, while source routes every non-`0x2202` ID into the GL064-style write path.
- **Design implication:** do not use the printed sector maximum as a complete software timeout, and do not invent an additional preprogram allowance. A safe bounded-wait policy still needs the exact S71 part/ID set, all supported device protocols, a chosen engineering cap/UX policy despite the unbounded datasheet preprogram component, flash reset/error cleanup semantics, and caller error propagation. ### F-011 startup ordering and stack comparison (2026-10-14)

- The thumbnail loader is not normally called while `SETTINGS.TXT` is open for an F-011 settings transaction. These are hypotheses, not established causes. The no-start-thumbnail build confirms the freeze is in or triggered by the thumbnail call, while the direct-read diagnostic still hanging means the recovery-read scan alone does not explain it.
- Compared isolated `-fstack-usage` builds of F-011 parent `6bdf5588` and F-011 commit `983dd13` with the same devkitARM compiler.
