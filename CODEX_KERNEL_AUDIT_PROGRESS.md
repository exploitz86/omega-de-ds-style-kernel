### F-009 filename truncation confirmed; compact alias option identified (2026-10-15 23:38 UTC)

This avoids allocating a full long-name table, but every path/identity consumer must be reviewed: save naming, artwork names, favorites/recents, style loading, and visible disambiguation could change if aliases are used indiscriminately. ### F-022 interrupt-wait hypothesis and revision compatibility evidence (2026-10-15 23:30 UTC)

The libgba header maps `VBlankIntrWait()` to BIOS SWI 5 and documents that IME=0 masks all interrupts. This means the call relies on BIOS/IRQ wait behavior and the previously initialized VBlank dispatcher.
- **Hypothesis status:** the initial thought that `IME=0` necessarily makes SWI 5 hang is **not verified and should not be reported as a defect**. A widely used reverse-engineered GBA BIOS reference says `IntrWait` forces IME on and SWI 5 delegates to it, which would make this call return while also re-enabling interrupts; however, an official Nintendo SWI reference establishing that side effect was not located in this pass. Treat this secondary evidence as a lead, not proof. No device test was run. The unconditional final `REG_IME=1` is a verified state overwrite, but all in-repository `Chip_Erase` calls are through the main UI after startup enabled IME, so a user-visible regression from losing an initially disabled state is not demonstrated.

The official [DE product page](https://www.ezflash.cn/product/ez-flash-omega-definitive-edition/) describes the 512-Mbit NOR capacity but does not identify the installed chip model.

Existing tests asserted installed bundled style filenames at `v7.3`, but the authoritative `docs/manager/packages/current/manifest.json` and package binaries use version `7.4`; baseline failed on the first stale expectation. The two calls to APIs taking `u32 *` cast at those boundaries. `make` passes; focused Cppcheck is being checked before finalizing.
- `F-003` — Severity: high; category: confirmed storage correctness/resource cleanup. `source/Ezcard_OP.c:88-124,127-154`, `source/ff15/diskio.c:89-113,139-162`. `Read_SD_sectors` retried a timed-out sector read twice, then unconditionally DMA-copied the last SRAM contents and returned 0. `disk_read` passed that return through as `DRESULT`, so FatFs received `RES_OK` after hardware timeout and could consume corrupted/stale sectors. `Write_SD_sectors` returned 1 on timeout without calling `SD_Disable()`, leaving the device interface enabled. The return convention is demonstrated by success returning 0 and write timeout returning 1; `DRESULT` uses `RES_OK=0`, `RES_ERROR=1`. Fixed: failed reads now disable SD and return before DMA; failed writes disable SD before returning error. Static/source review passes; no cartridge hardware access, so real timeout behavior and device recovery remain unverified.
- `F-004` — Severity: medium; category: confirmed memory safety / deep navigation. `source/ezkernelnew.c:513-516,14190-14200,15376-15400`. The per-directory selection stacks were fixed at 100 entries, while `currentpath` is 256 bytes and folder entry/restore increments and indexes `folder_select` without a depth guard. A valid path deeper than 99 nested folders can index beyond the arrays. Fixed by sizing both stacks to `MAX_path_len`; adversarial review also found the folder-entry path builder silently truncated long paths before changing directory. It now rejects a path that cannot fit in `currentpath` and updates `currentpath` only after `f_chdir` succeeds, preserving the path/depth invariant. Static Cppcheck and source review pass; filesystem integration remains untested.

- `F-015` — Severity: high; category: confirmed RTS integrity/error handling. `source/ezkernelnew.c:4780-4810`, `source/GBApatch.c:937-1000`. `LoadRTSfile` ignored read errors/short counts and wrote stale EWRAM data into SRAM while loading a fixed 0x70000-byte state; `Check_RTS` ignored the loader result and claimed newly created RTS files were full size even after a short/error write. Fixed by requiring the exact expected file size, checking each read before its page write, checking initialization writes and close, restoring the page mapping on failure, and propagating load failure so the game launch aborts. Production build passes; real SD/RTS hardware behavior remains untested.
- `F-016` — Severity: medium; category: confirmed bounded-string safety. `source/GBApatch.c:937-955`, `source/ezkernelnew.c:15584-15620`. `Check_RTS` and the FRAM save menu copied all 100 bytes of a fixed filename buffer and then called `strlen`; a full-width non-terminated filename could read beyond the object and produce invalid extension indexes. Both paths now find a terminator within the source capacity, reject missing/too-short names, and terminate the local copy before extension replacement. Production build and focused Cppcheck pass; maximum-width hardware filenames are not exercised on cartridge.
- `F-017` — Severity: medium; category: confirmed save-file recovery correctness. `source/ezkernelnew.c:4823-4900`. A failed first-time `.sav` creation could leave a truncated file that a later launch treated as an existing save. `SavefileWrite` now closes and removes the newly created file after short/error writes or failed close. The full audit script passed after this fix; no physical card fault test was run.
- `F-018` — Severity: high; category: confirmed memory overwrite in NOR metadata loading. `source/Ezcard_OP.c:419-425`. `Read_NOR_info` indexed `pNorFS` through a `u16 *` but looped `sizeof(FM_NOR_FS) * MAX_NOR` times, treating the metadata byte count as a halfword count. With 64 records of 132 bytes, each call wrote 16,896 bytes into an 8,448-byte array, overflowing by another 8,448 bytes. The current and known-good linker maps show this clobbered `SET_info_buffer` and cheat-parser EWRAM globals. Fixed the loop bound to the destination's halfword count and documented the unit. `make`, focused Cppcheck, and the full audit script pass. No cartridge run was performed.
- `F-019` — Severity: high; category: confirmed NOR install data-integrity and error-propagation failure. `source/NORflash_OP.c:215-363`; callers `source/ezkernelnew.c:16277,16321,16360,16367`. `Loadfile2NOR` treated `f_open` failure as success, read header fields and ROM blocks without checking seek/read results or returned byte counts, erased each destination ROM block before reading its source data, and programmed a full 128 KiB from a buffer whose final partial-block tail was stale. It also published `pNorFS[game_total_NOR]` before programming completed and leaked the opened file on the capacity return. Both PSRAM/NOR add-on callers also built the global `iTrimSize` from unchecked last-block probes; failed opens or short reads could leave the prior game's trim point active. Fixed by validating size/header reads, exact per-block I/O, 0xFF-padding the final block, reading each source block before erasing its destination ROM block, closing on failures, checking the filename bound, and committing/saving metadata only after every block is read/programmed and the source closes successfully. Physical NOR/SD behavior is untested.
- `F-020` — Severity: high; category: confirmed NOR catalog bounds and malformed-metadata handling. `source/NORflash_OP.c:232-235,365-428`. Install could write `pNorFS[game_total_NOR]` without a slot guard. During catalog scan, the `count > MAX_NOR` check came after dereferencing `pNorFS[count]`, so a 65th record accessed beyond the 64-entry array. Persisted `filesize` was also trusted before advancing the mapped NOR address, allowing zero, unaligned, or oversized sizes to stall or leave the 64 MiB mapping. Fixed with a pre-index slot bound and checks for nonzero block-aligned sizes and remaining NOR capacity before advancing. `make`, focused Cppcheck, and the full audit script pass; malformed on-cartridge metadata was not injected.
- `F-021` — Severity: medium; category: confirmed interrupt-state cleanup defect. `source/NORflash_OP.c:374-375,417-431`. `GetFileListFromNor` disabled interrupts for its scan and returned directly after reaching the 64 MiB page limit without restoring `REG_IME`; a full-size NOR catalog could leave interrupts disabled. Fixed by saving the incoming interrupt-enable value and restoring it through the common scan exit. `make`, focused Cppcheck, and the full audit script pass; hardware interrupt behavior is untested.
- `F-022` — Severity: medium; category: open flash-operation liveness risk. `source/NORflash_OP.c:32-75,87-118,133-211`; `source/Ezcard_OP.c:339-403`. NOR erase/program and auxiliary S71 metadata routines poll hardware with no finite timeout, and their `void` APIs cannot report a failed operation to callers. If a device stays busy or stops responding, the kernel can remain blocked in the loop. No bound was added because a safe timeout needs the supported chip's erase/program maximums, its status-bit protocol, and consistent failure propagation; no hardware fault injection is available here. This is a source-confirmed unbounded wait with hardware-specific failure likelihood untested, not evidence that normal cartridges hang.
- `F-023` — Severity: medium; category: confirmed out-of-bounds read in NOR/PSRAM trim detection. `source/GBApatch.c:303-355`; caller `source/ezkernelnew.c:15809-15838`. `SetTrimSize` computed `(romsize - 1) % iSize - 1` in unsigned arithmetic. For a valid ROM whose size is 1 modulo the 128 KiB cache block, the result wrapped to `UINT_MAX`; the subsequent byte read and reverse scan indexed outside `pReadCache`. When the local offset was small, `bottom - 16` could also underflow and skip the intended bounded scan. Fixed by validating non-null/nonzero inputs, computing the modulo first, decrementing only when positive, and comparing `bottom` directly against `PATCH_LENGTH + 16`. `make`, focused Cppcheck, and the full audit script pass; no cartridge test was performed.
