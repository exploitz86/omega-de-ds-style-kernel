## Findings ledger

- `F-001` — Severity: low; category: maintenance/test correctness. `tests/browser-installer.mjs:184,187,203-204`. Existing tests asserted installed bundled style filenames at `v7.3`, but the authoritative `docs/manager/packages/current/manifest.json` and package binaries use version `7.4`; baseline failed on the first stale expectation. Updated all four expected filenames to `v7.4`. `node tests/browser-installer.mjs` now passes. Root cause is stale regression expectations, not installer behavior.
- `F-002` — Severity: low / needs triage; category: portability warning. `source/ezkernelnew.c:4926,5425,5480,5521`. Cppcheck flags arithmetic on `void *` cartridge addresses. This is a GNU C extension (the devkitARM Makefile uses GNU make rules and does not request strict ISO C), and the expressions are byte offsets into memory-mapped PSRAM; no behavior defect is established. Deferred unless the exact devkitARM compiler flags show a portability/build issue.
- `F-003` — Severity: high; category: confirmed storage correctness/resource cleanup. `source/Ezcard_OP.c:88-124,127-154`, `source/ff15/diskio.c:89-113,139-162`. `Read_SD_sectors` retried a timed-out sector read twice, then unconditionally DMA-copied the last SRAM contents and returned 0. `disk_read` passed that return through as `DRESULT`, so FatFs received `RES_OK` after hardware timeout and could consume corrupted/stale sectors. `Write_SD_sectors` returned 1 on timeout without calling `SD_Disable()`, leaving the device interface enabled. The return convention is demonstrated by success returning 0 and write timeout returning 1; `DRESULT` uses `RES_OK=0`, `RES_ERROR=1`. Fixed: failed reads now disable SD and return before DMA; failed writes disable SD before returning error. Static/source review passes; no cartridge hardware access, so real timeout behavior and device recovery remain unverified.
- `F-004` — Severity: medium; category: confirmed memory safety / deep navigation. `source/ezkernelnew.c:513-516,14190-14200,15376-15400`. The per-directory selection stacks were fixed at 100 entries, while `currentpath` is 256 bytes and folder entry/restore increments and indexes `folder_select` without a depth guard. A valid path deeper than 99 nested folders can index beyond the arrays. Fixed by sizing both stacks to `MAX_path_len`; adversarial review also found the folder-entry path builder silently truncated long paths before changing directory. It now rejects a path that cannot fit in `currentpath` and updates `currentpath` only after `f_chdir` succeeds, preserving the path/depth invariant. Static Cppcheck and source review pass; filesystem integration remains untested.
- `F-005` — Severity: medium; category: confirmed memory safety. `source/showcht.c:994-1017`; caller `source/ezkernelnew.c:15790-15804,15909-15912`. `Check_cheat_file` copied exactly 100 bytes from the selected filename into a 100-byte local array and called `strlen` without forcing a terminator. The Recent Played caller can pass a 100-character basename, whose extension remains at the buffer edge and causes this code to run. Fixed by using a 200-byte local buffer matching `current_filename`, bounded copy with explicit termination, and a length check before rewriting the extension. Validation: Cppcheck/static review and edge-case call-path analysis; cartridge-side cheat loading is not run.
- `F-006` — Severity: low / probable localization maintenance issue. `launcher_text_languages.json` vs `source/launcher_text_languages.json`. Both are versioned catalogs. At v7.3, history shows only the source catalog was updated; the root catalog has since lacked keys present in the source catalog (including boot-to settings and additional labels). Repository references do not establish a single canonical consumer: README points users to DS Style Customiser, `source/launcher_text_custom.h` says the customizer writes `launcher_runtime_text.h`, and no in-tree generator references either catalog. Values also differ across locale variants. Deferred: do not sync catalogs until intended consumers and authority are established; no runtime defect confirmed.
- `F-007` — Severity: medium; category: confirmed hardware-memory correctness. `source/GBApatch.c:41-88`, called by ROM patch routines at lines 95-1441. `Write` selected the PSRAM page for the starting address once, then wrote all halfwords linearly. The same firmware maps PSRAM in 8 MiB banks (page selector increments by `0x1000` in `Loadfile2PSRAM`), so any patch payload crossing a bank boundary could write its tail into the wrong physical page. Fixed by splitting the PSRAM write into per-bank chunks and selecting each page; unaligned PSRAM patch offsets now return without issuing halfword writes. The damaged TODO comment also obscured this invariant and was replaced. Cppcheck/source verification only; no hardware test or target build yet.
- `F-008` — Severity: medium; category: confirmed malformed-input bounds/resource lifecycle. `source/showcht.c:1039-1080`. `Check_cheat_file` reads a binary index as pairs of 32-bit values, but looped while `i < filesize / 4` and then accessed `tempbuff[i + 1]`. A file containing an odd number of 32-bit words could therefore compare a word beyond the bytes read; a no-match scan also returned without closing `GameID2cht.bin`. Fixed by checking `f_read`, iterating only while a complete pair exists in the actual returned byte count, ignoring an incomplete trailing record, and closing the file after no-match/error. Existing match path already closes before returning. Cppcheck and source review pass; no malformed-file runtime harness or cartridge test.
- `F-009` — Severity: low; category: confirmed limitation / deferred memory-layout change. `source/ezkernel.h:22-28`, `source/ezkernelnew.c:473-481,14145-14159`; FatFs permits 255-byte names (`source/ff15/ffconf.h:116-118,148`). Folder and file list records hold only 99 characters, and the launcher truncates longer names, so such valid files/directories may display ambiguously or fail to open. The file list is constrained to a 64 KiB PSRAM window by a compile-time size assertion, while the existing compact record is 104 bytes; expanding all 512 records to full LFN storage would exceed that window. Deferred pending a design that preserves the PSRAM/EWRAM layout and offers a clear UI outcome; no broad structure or memory-map change is justified in this audit.
- `F-010` — Severity: medium; category: confirmed uninitialized-state defect. `source/ezkernelnew.c:13994,14121-14271` (line numbers refresh after edits). Cppcheck on the now-available devkitPro Codespace reported `game_folder_total` possibly uninitialized when `f_opendir` failed, since the aggregate was only assigned in the successful-open branch, and later used for selection clamping and launch decisions. A first branch-level initialization did not silence the warning because the main loop can transition to SD listing through additional control flow; the local is now initialized at declaration and the SD recount branch also resets it before listing. This guarantees a defined empty-list fallback. Production build passes; fresh targeted Cppcheck exits 0 with no diagnostics after the unconditional initialization. Browser suite and whitespace/JS checks passed on the immediately preceding full-script run; they should be rerun for final quality gate.
- `F-011` — Severity: medium; category: confirmed persistence error-handling defect with data-loss risk; **resolved in current branch**. The former `Launcher_SaveUnifiedSettings` at `source/ezkernelnew.c:10923` opened `SETTINGS.TXT` with `FA_CREATE_ALWAYS`, ignored serialization/close results, and removed legacy sources after open success. It now streams the plain-text payload to checksummed `/SYSTEM/SETTINGS.TMP`, makes and verifies `/SYSTEM/SETTINGS.BAK` before removing the primary, then renames the temp to canonical `/SYSTEM/SETTINGS.TXT`. Startup restores the backup if interrupted after primary removal; if primary remains intact, it remains authoritative and an incomplete temp is discarded. The backup preserves readable text and external installer edits; stale checksum comments from edits are accepted when there are no in-progress transaction artifacts. Host tests (`tests/settings-store-host.c`, run with `scripts/test-settings-store-host.sh`) pass legacy/plain-text fallback, installer-style edits, injected sector-write interruptions, first-save failure, flush failure, full media, serializer overflow, and missing-primary recovery. The full audit script passes, including target build, browser/JS checks, whitespace, and Cppcheck. Limits: the in-memory disk models reported I/O errors and atomic sector writes; physical cartridge/card and genuine mid-sector power-loss behavior remain unverified.
- `F-012` — Severity: high; category: confirmed malformed-input memory safety in cheat parsing. `source/showcht.c:252-535,606-660,795-900`. CHEAT files are read from SD and determine section/key/value text. The parser could overflow 50-byte section buffers, leave a maximum-length key unterminated before `strcmp`, append multiline values past the 6000-byte global buffer, copy unchecked address/value digits into 8/3-byte buffers, underflow a section index when a selected record had no earlier section, and decrement an empty value length below zero before returning it as unsigned. Fixed by bounding and terminating section/key copies, resetting section lengths at each header, checking multiline capacity, providing space for an address terminator, rejecting an overlong code row without retaining partial entries, bounding value digits, guarding section lookup, and rejecting empty values before code parsing. Target build and focused Cppcheck pass; physical cheat-file loading is not hardware-tested.
- `F-013` — Severity: high; category: confirmed save integrity/error propagation. `source/ezkernelnew.c:4663-4702,9118-9199,15555-15596`. `Loadsavefile` ignored `f_read` status/byte counts and copied the EWRAM read buffer into cartridge SRAM regardless, then reported success; a short or failed SD read could install stale or partial save data. Fixed by reading the capped save into the full 128 KiB EWRAM staging buffer, requiring an exact successful read before switching/writing SRAM banks, returning failure without touching SRAM on a read error, and propagating the error so normal/NOR/FRAM load callers do not report success or continue launching. Production build and focused Cppcheck pass; physical SD/SRAM failure behavior is untested.
- `F-014` — Severity: high; category: confirmed save recovery persistence failure handling. `source/ezkernelnew.c:4702-4840,9215-9280,15630-15650`. `Save_savefile` and `SavefileWrite` ignored `f_write` results and close status, then returned success after short/error writes. `Check_save_flag` cleared the pending FRAM recovery marker regardless of whether its save reached the SD card, which could discard the only recovery prompt after a failed write; FRAM save also displayed success unconditionally. Fixed by checking every write result/byte count and `f_close`, restoring the SRAM bank mapping, propagating failures, retaining the pending marker unless the save succeeds or the user explicitly chooses B to discard, and reporting FRAM save failure. Full production build passes; storage fault behavior remains hardware-unverified.
- `F-015` — Severity: high; category: confirmed RTS integrity/error handling. `source/ezkernelnew.c:4780-4810`, `source/GBApatch.c:937-1000`. `LoadRTSfile` ignored read errors/short counts and wrote stale EWRAM data into SRAM while loading a fixed 0x70000-byte state; `Check_RTS` ignored the loader result and claimed newly created RTS files were full size even after a short/error write. Fixed by requiring the exact expected file size, checking each read before its page write, checking initialization writes and close, restoring the page mapping on failure, and propagating load failure so the game launch aborts. Production build passes; real SD/RTS hardware behavior remains untested.
- `F-016` — Severity: medium; category: confirmed bounded-string safety. `source/GBApatch.c:937-955`, `source/ezkernelnew.c:15584-15620`. `Check_RTS` and the FRAM save menu copied all 100 bytes of a fixed filename buffer and then called `strlen`; a full-width non-terminated filename could read beyond the object and produce invalid extension indexes. Both paths now find a terminator within the source capacity, reject missing/too-short names, and terminate the local copy before extension replacement. Production build and focused Cppcheck pass; maximum-width hardware filenames are not exercised on cartridge.
