## 2026-10-16 15:40 UTC — S71 one-way marker command compatibility checked

- **Phase/subsystem:** F-022 S71 metadata recovery. **Objective:** determine whether a post-commit shadow invalidation marker can use commands supported by both source-level S71 paths without relying on undocumented repeated programming of the same flash word.
- **Primary documentation reviewed:** Spansion [S29GL-A datasheet](https://www.farnell.com/datasheets/1500802.pdf), §9.4.1, states standard single-word programming is supported, while programming the same word repeatedly without erase needs a modified method. Infineon [S29PL-J datasheet](https://www.infineon.com/assets/row/public/documents/10/49/infineon-s29pl-j-128--128--64--32-mbit-8-8-4-2m-x-16-bit-3-v-flash-with-enhanced-versatileio-datasheet-en.pdf?fileId=8ac78c8c7d0d8da4017d0ed5806154f0), §15.5, describes its four-cycle word program and 1->0-only behavior. This supports programming two *distinct* one-time halfword markers: active at the very end of a 64-byte header (last write), retirement in a separate still-erased halfword. Header 8,448-byte payload + 64-byte header = 8,512 bytes, still a multiple of the existing 32-byte GL write-buffer transfer unit.
- **Design candidate, not code:** shadow active only if its immutable header/data CRC validates, its active marker matches, and retirement marker remains `0xFFFF`. After primary candidate plus header verify, program the distinct retirement halfword to zero; any changed/non-erased retirement value makes the shadow ineligible. Primary-valid always outranks shadow. If primary is invalid, an active shadow is recoverable; if shadow is retired and primary is legacy, use primary. Put the active marker at the last halfword so a partial shadow write cannot make the copy valid before its payload/header. This avoids a second program of one word and ordinary successful downgrade would see the retired shadow.
- **Residual ambiguity:** if power loss or a program failure occurs before *any* bit of the retirement marker changes, the shadow remains valid. A later older firmware can rewrite the raw primary, which is indistinguishable from an interrupted new-firmware primary write to a new reader. Thus source docs support the marker command, but do not yet prove a fully downgrade-safe transaction under every failed retirement. Need test and assess whether another persistent state signal or semantic catalog validation can resolve it; do not integrate or claim full compatibility yet.
- **Next:** create the host model with distinct marker words and inject cuts before/during/after active and retire programming, shadow/primary erase and write, then include an older-firmware raw rewrite after each state. If the model exposes a remaining ambiguity that cannot be safely resolved, document F-032 as not fixed rather than accepting a silent stale catalog.

- `F-003` — Severity: high; category: confirmed storage correctness/resource cleanup. `source/Ezcard_OP.c:88-124,127-154`, `source/ff15/diskio.c:89-113,139-162`. `Read_SD_sectors` retried a timed-out sector read twice, then unconditionally DMA-copied the last SRAM contents and returned 0. `disk_read` passed that return through as `DRESULT`, so FatFs received `RES_OK` after hardware timeout and could consume corrupted/stale sectors. `Write_SD_sectors` returned 1 on timeout without calling `SD_Disable()`, leaving the device interface enabled. The return convention is demonstrated by success returning 0 and write timeout returning 1; `DRESULT` uses `RES_OK=0`, `RES_ERROR=1`. Fixed: failed reads now disable SD and return before DMA; failed writes disable SD before returning error. Static/source review passes; no cartridge hardware access, so real timeout behavior and device recovery remain unverified.

The per-directory selection stacks were fixed at 100 entries, while `currentpath` is 256 bytes and folder entry/restore increments and indexes `folder_select` without a depth guard. A valid path deeper than 99 nested folders can index beyond the arrays. Fixed by sizing both stacks to `MAX_path_len`; adversarial review also found the folder-entry path builder silently truncated long paths before changing directory. The Recent Played caller can pass a 100-character basename, whose extension remains at the buffer edge and causes this code to run. - `F-016` — Severity: medium; category: confirmed bounded-string safety. `source/GBApatch.c:937-955`, `source/ezkernelnew.c:15584-15620`. `Check_RTS` and the FRAM save menu copied all 100 bytes of a fixed filename buffer and then called `strlen`; a full-width non-terminated filename could read beyond the object and produce invalid extension indexes. Both paths now find a terminator within the source capacity, reject missing/too-short names, and terminate the local copy before extension replacement. Production build and focused Cppcheck pass; maximum-width hardware filenames are not exercised on cartridge.
- `F-017` — Severity: medium; category: confirmed save-file recovery correctness. `source/ezkernelnew.c:4823-4900`. A failed first-time `.sav` creation could leave a truncated file that a later launch treated as an existing save. `SavefileWrite` now closes and removes the newly created file after short/error writes or failed close. The full audit script passed after this fix; no physical card fault test was run.
- `F-018` — Severity: high; category: confirmed memory overwrite in NOR metadata loading. `source/Ezcard_OP.c:419-425`. `Read_NOR_info` indexed `pNorFS` through a `u16 *` but looped `sizeof(FM_NOR_FS) * MAX_NOR` times, treating the metadata byte count as a halfword count. With 64 records of 132 bytes, each call wrote 16,896 bytes into an 8,448-byte array, overflowing by another 8,448 bytes. The current and known-good linker maps show this clobbered `SET_info_buffer` and cheat-parser EWRAM globals. Fixed the loop bound to the destination's halfword count and documented the unit. `make`, focused Cppcheck, and the full audit script pass. No cartridge run was performed.
- `F-019` — Severity: high; category: confirmed NOR install data-integrity and error-propagation failure. `source/NORflash_OP.c:215-363`; callers `source/ezkernelnew.c:16277,16321,16360,16367`. `Loadfile2NOR` treated `f_open` failure as success, read header fields and ROM blocks without checking seek/read results or returned byte counts, erased each destination ROM block before reading its source data, and programmed a full 128 KiB from a buffer whose final partial-block tail was stale. It also published `pNorFS[game_total_NOR]` before programming completed and leaked the opened file on the capacity return. Both PSRAM/NOR add-on callers also built the global `iTrimSize` from unchecked last-block probes; failed opens or short reads could leave the prior game's trim point active. Fixed by validating size/header reads, exact per-block I/O, 0xFF-padding the final block, reading each source block before erasing its destination ROM block, closing on failures, checking the filename bound, and committing/saving metadata only after every block is read/programmed and the source closes successfully. The shared trim-probe helper checks size, seek, exact read count, and close before updating `iTrimSize`; errors are shown rather than reusing stale state. `make`, focused Cppcheck, and the full audit script pass. Physical NOR/SD behavior is untested.
- `F-020` — Severity: high; category: confirmed NOR catalog bounds and malformed-metadata handling. `source/NORflash_OP.c:232-235,365-428`. Install could write `pNorFS[game_total_NOR]` without a slot guard. During catalog scan, the `count > MAX_NOR` check came after dereferencing `pNorFS[count]`, so a 65th record accessed beyond the 64-entry array. Persisted `filesize` was also trusted before advancing the mapped NOR address, allowing zero, unaligned, or oversized sizes to stall or leave the 64 MiB mapping. Fixed with a pre-index slot bound and checks for nonzero block-aligned sizes and remaining NOR capacity before advancing. `make`, focused Cppcheck, and the full audit script pass; malformed on-cartridge metadata was not injected.
- `F-021` — Severity: medium; category: confirmed interrupt-state cleanup defect. `source/NORflash_OP.c:374-375,417-431`. `GetFileListFromNor` disabled interrupts for its scan and returned directly after reaching the 64 MiB page limit without restoring `REG_IME`; a full-size NOR catalog could leave interrupts disabled. Fixed by saving the incoming interrupt-enable value and restoring it through the common scan exit. `make`, focused Cppcheck, and the full audit script pass; hardware interrupt behavior is untested.
- `F-022` — Severity: medium; category: open flash-operation liveness risk. `source/NORflash_OP.c:32-75,87-118,133-211`; `source/Ezcard_OP.c:339-403`. NOR erase/program and auxiliary S71 metadata routines poll hardware with no finite timeout, and their `void` APIs cannot report a failed operation to callers. If a device stays busy or stops responding, the kernel can remain blocked in the loop. No bound was added because a safe timeout needs the supported chip's erase/program maximums, its status-bit protocol, and consistent failure propagation; no hardware fault injection is available here. This is a source-confirmed unbounded wait with hardware-specific failure likelihood untested, not evidence that normal cartridges hang.
- `F-023` — Severity: medium; category: confirmed out-of-bounds read in NOR/PSRAM trim detection. `source/GBApatch.c:303-355`; caller `source/ezkernelnew.c:15809-15838`. `SetTrimSize` computed `(romsize - 1) % iSize - 1` in unsigned arithmetic. For a valid ROM whose size is 1 modulo the 128 KiB cache block, the result wrapped to `UINT_MAX`; the subsequent byte read and reverse scan indexed outside `pReadCache`. When the local offset was small, `bottom - 16` could also underflow and skip the intended bounded scan. Fixed by validating non-null/nonzero inputs, computing the modulo first, decrementing only when positive, and comparing `bottom` directly against `PATCH_LENGTH + 16`. `make`, focused Cppcheck, and the full audit script pass; no cartridge test was performed.
- `F-024` — Severity: low; category: confirmed rendering/source-stride defect in the NOR format progress redraw. `source/NORflash_OP.c` `Chip_Erase`; `images/blank/MENU.h` and `images/dark/MENU.h` define 168x110 menu assets; `source/draw.c` `DrawPic` treats its `w` parameter as source stride. - `F-026` — Severity: high; confidence: high; category: verified user-stack/static-data overlap. `Makefile`, `source/reset.s`, production map, and `Launcher_DrawStartLastThumb`/thumbnail call path.
